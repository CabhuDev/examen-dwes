✅ Ver solución comentada 
/**
 * Devuelve los días recibidos vía POST que sean válidos,
 * o false si no se recibe nada o alguno no es válido.
 * @param  array       $diasValidos  claves de días aceptados (['L','M',...])
 * @return array|false
 */
function validarDatosRecibidos(array $diasValidos)
{
    // 1) ¿Llega 'dias' por POST y es un array?
    if (!isset($_POST['dias']) || !is_array($_POST['dias'])) {
        return false;
    }

    // 2) Cada día recibido debe estar entre los válidos
    foreach ($_POST['dias'] as $dia) {
        if (!in_array($dia, $diasValidos)) {
            return false;   // alguno no es válido
        }
    }

    // 3) Todo correcto: devolvemos los días seleccionados
    return $_POST['dias'];
}
Por qué:
• isset() + is_array() → evita avisos si no llega nada.
• in_array() → comprueba pertenencia al conjunto válido (funciones básicas de PHP, no hay que memorizar nada raro).
• Devolver false en error encaja con el === false del fragmento A2.

// $eventos: ['L'=>['Reunión','Gimnasio'], 'V'=>['Cine'], ...]

function generarEventos(array $diasSeleccionados, array $eventos)

📚 Teoría · PHP básico (Unidad 1)

1. Recoger datos de un formulario

Los formularios envían datos por $_GET (querystring) o $_POST (cuerpo). Siempre hay que comprobar que el dato llega antes de usarlo:

$titulo = isset($_POST['titulo']) ? trim($_POST['titulo']) : '';
  • isset() → ¿existe y no es null? · empty() → ¿está vacío?
  • trim() → quita espacios sobrantes · htmlspecialchars() → evita inyección HTML al re-mostrar.
  • Checkboxes/múltiples → name="campo[]" llega como array.

2. Arrays (lo que más se usa en todo el módulo)

  • Indexado: ['Cine','Teatro'] · Asociativo: ['L'=>'Lunes'].
  • in_array($v,$arr) ¿está el valor? · array_keys($arr) claves · count($arr) tamaño · $arr[] = $x añade al final.
  • Recorrer: foreach ($arr as $clave => $valor) { ... }

3. Funciones y organización del código

Separar la lógica en funciones reutilizables. Tipar parámetros/retorno cuando se pueda y devolver un valor coherente con cómo se usa la función (p. ej. false en error, un array/número en éxito).

/**
 * Inserta una coordenada (x,y) en la tabla coordenadas.
 *
 * @param  PDO  $pdo  conexión PDO activa
 * @param  int  $x    coordenada X (0-15)
 * @param  int  $y    coordenada Y (0-15)
 * @return int|false  nº de filas insertadas (1) o false si hay error
 */
function insertarCoordenadas(PDO $pdo, int $x, int $y)
{
    try {
        // Consulta parametrizada (evita inyección SQL)
        $sql = "INSERT INTO coordenadas (x, y) VALUES (:x, :y)";
        $stmt = $pdo->prepare($sql);

        // Enlace de parámetros indicando tipo INT
        $stmt->bindValue(':x', $x, PDO::PARAM_INT);
        $stmt->bindValue(':y', $y, PDO::PARAM_INT);

        $stmt->execute();

        // rowCount() = nº de filas afectadas (1 si todo OK)
        return $stmt->rowCount();

    } catch (PDOException $ex) {
        // El check de la tabla o el PRIMARY KEY duplicado caerán aquí.
        // Devolvemos false como espera el fragmento B5.
        return false;
    }
}
Por qué este enfoque:
• Consulta parametrizada con :x/:y → protege de SQL injection.
• try/catch sobre PDOException → ya hay un CHECK en la tabla y un PRIMARY KEY (x,y); si se intenta insertar fuera de rango o duplicado, PDO lanza excepción.
• rowCount() retorna 1 si insertó, lo que encaja con echo "Filas insertadas=$filasInsertadas".
• return false en el catch encaja con if ($filasInsertadas===false).

/**
 * Inserta una nueva película.
 *
 * @param  PDO   $pdo    conexión PDO
 * @param  array $datos  ['titulo','genero','direccion','duracion','argumento','anio']
 * @return int|false     ID generado por AUTO_INCREMENT, o false en error
 */
function insertarPelicula(PDO $pdo, array $datos)
{
    try {
        $sql = "INSERT INTO peliculas
                (titulo, genero, direccion, duracion, argumento, anio)
                VALUES (:titulo, :genero, :direccion, :duracion, :argumento, :anio)";

        $stmt = $pdo->prepare($sql);

        $stmt->bindValue(':titulo',    $datos['titulo'],    PDO::PARAM_STR);
        $stmt->bindValue(':genero',    $datos['genero'],    PDO::PARAM_INT);
        $stmt->bindValue(':direccion', $datos['direccion'], PDO::PARAM_STR);
        $stmt->bindValue(':duracion',  $datos['duracion'],  PDO::PARAM_INT);
        $stmt->bindValue(':argumento', $datos['argumento'], PDO::PARAM_STR);
        $stmt->bindValue(':anio',      $datos['anio'],      PDO::PARAM_INT);

        $stmt->execute();

        // lastInsertId devuelve el id que MySQL acaba de auto-generar.
        return (int) $pdo->lastInsertId();

    } catch (PDOException $ex) {
        return false;
    }
}

• Si te piden DELETE → igual: rowCount().

📚 Teoría · Bases de datos con PDO

1. ¿Qué es PDO y por qué se usa?

PDO (PHP Data Objects) es la capa de abstracción de bases de datos oficial de PHP. Permite conectarse a múltiples motores (MySQL, PostgreSQL, SQLite, Oracle...) usando siempre la misma API. Si mañana cambias de MySQL a PostgreSQL, solo cambias el DSN.

Ventajas frente a las funciones antiguas (mysql_*, deprecadas) o mysqli:

  • Consultas preparadas nativas → previenen inyección SQL.
  • Manejo de errores con excepciones (PDOException) en lugar de comprobar false a cada paso.
  • API uniforme entre motores.

2. El DSN (Data Source Name)

El DSN es la cadena que le dice a PDO a qué base de datos conectarse. Estructura:

driver:host=HOST;port=PUERTO;dbname=BD;charset=CHARSET

Ejemplo (de tu DWES02):

mysql:host=localhost;port=3306;dbname=dwes02;charset=utf8mb4

Constructor: new PDO($dsn, $usuario, $password, $opciones).

3. Configuración correcta de la conexión

$pdo = new PDO($dsn, DB_USER, DB_PASS, [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,    // Lanza excepciones ante errores
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,           // fetch() devuelve array asociativo
    PDO::ATTR_EMULATE_PREPARES   => false                       // Prepared statements reales del driver
]);
Clave: ERRMODE_EXCEPTION es la opción más importante. Sin ella, los errores SQL se ignoran silenciosamente (PDO devuelve false y tú no te enteras).

4. Consultas preparadas — el corazón de PDO

Una consulta preparada separa el SQL de los datos. El SQL se compila una vez, y los datos se "atan" después como parámetros, nunca se interpolan en el SQL.

Con parámetros con nombre (recomendado, más legible)
$sql = "SELECT * FROM peliculas WHERE anio = :anio AND genero = :gen";
$stmt = $pdo->prepare($sql);
$stmt->bindValue(':anio', $anio, PDO::PARAM_INT);
$stmt->bindValue(':gen',  $gen,  PDO::PARAM_INT);
$stmt->execute();
Con parámetros posicionales
$stmt = $pdo->prepare("SELECT * FROM peliculas WHERE anio = ? AND genero = ?");
$stmt->execute([$anio, $gen]);   // ¡Forma compacta!

5. bindParam vs bindValue

  • bindParam(':x', $var): liga la variable por referencia. El valor que tenga $var en el momento de execute() es el que se usa.
  • bindValue(':x', 5): liga el valor en ese instante. Aunque la variable cambie después, el valor ligado no.

En la práctica, para inserciones puntuales bindValue suele ser más claro. bindParam es útil dentro de bucles donde reutilizas la sentencia y solo cambia la variable.

6. Leer resultados

  • fetch(): una fila cada vez. Devuelve false cuando no hay más. Ideal para bucles while.
  • fetchAll(): todas las filas a la vez en una matriz. Cómodo, pero gasta memoria si la tabla es enorme.
  • fetchColumn(): un solo valor (la primera columna de la primera fila). Útil para COUNT(*), SUM(...), etc.

Modos de fetch: PDO::FETCH_ASSOC (claves de texto), FETCH_NUM (claves numéricas), FETCH_BOTH (las dos, por defecto), FETCH_OBJ (objeto stdClass), FETCH_CLASS (clase concreta).

7. INSERT, UPDATE, DELETE — métodos clave

  • $pdo->lastInsertId() → el AUTO_INCREMENT que MySQL generó tras el último INSERT en esa conexión.
  • $stmt->rowCount() → nº de filas afectadas. Útil para saber si UPDATE/DELETE realmente cambió algo.

8. Manejo de errores con try/catch

try {
    $stmt = $pdo->prepare($sql);
    $stmt->execute([$valor]);
    return $stmt->rowCount();
} catch (PDOException $ex) {
    error_log('Error BD: '.$ex->getMessage());
    return false;   // o lo que espere quien llama
}
Cuidado: el mensaje de error de PDOException puede contener información sensible (estructura de tablas, queries...). NUNCA lo muestres al usuario final. Registra con error_log().

9. Transacciones (cuando varias operaciones deben ser atómicas)

$pdo->beginTransaction();
try {
    $pdo->exec("UPDATE cuentas SET saldo = saldo - 100 WHERE id = 1");
    $pdo->exec("UPDATE cuentas SET saldo = saldo + 100 WHERE id = 2");
    $pdo->commit();   // Todo OK: confirma
} catch (PDOException $e) {
    $pdo->rollBack(); // Algo falló: revierte ambas operaciones
}

10. Cosas que NUNCA debes hacer

  • Concatenar datos en el SQL: "SELECT * FROM peliculas WHERE id = $id" ← inyección SQL.
  • Usar addslashes() en lugar de prepared statements: no protege en todos los charsets.
  • Devolver mensajes de excepción al cliente: filtran información sensible.
  • Olvidar el catch de PDOException: si está activo ERRMODE_EXCEPTION, una excepción no capturada tumba el script con un error visible.

 *
 * @param int|false $numero  número entero o false (no añadir)

function calcular($numero): int
{
    // 1. Si no existe la clave en sesión, inicializar a array vacío
    if (!isset($_SESSION['numeros'])) {
        $_SESSION['numeros'] = [];
    }

    // 2. Si hemos recibido un número válido (no false), lo añadimos
    if ($numero !== false) {

        // Si ya hay 5 o más, quitamos el más antiguo (primer elemento)
        if (count($_SESSION['numeros']) >= 5) {
            array_shift($_SESSION['numeros']);
        }

        // Añadimos el nuevo al final
        $_SESSION['numeros'][] = (int) $numero;
    }

    // 3. Devolver siempre la suma actual
    return array_sum($_SESSION['numeros']);
}
Puntos clave que evalúan:
• Inicializar el array si la clave no existe (if (!isset(...))).
• array_shift elimina el primero (más antiguo) — antes de añadir el nuevo, no después.
• Manejar el caso $numero === false (no se añade pero sí se devuelve la suma).
• array_sum sobre array vacío devuelve 0 → cubre el caso "sin números".

Conceptos fundamentales sobre sesiones, cookies y seguridad.

📚 Teoría · Sesiones y Cookies

1. El problema que resuelven

HTTP es un protocolo sin estado: cada petición es independiente, el servidor no recuerda nada de peticiones anteriores. Para que una web sepa "este usuario está logueado", "ha añadido X al carrito" o "su idioma preferido es ES", necesitamos algún mecanismo de persistencia entre peticiones. Para eso existen las cookies y las sesiones.

2. Cookie vs Sesión — la diferencia clave

CookieSesión
Vive en el navegador (lado cliente)Vive en el servidor (archivo o BD)
Visible y editable por el usuarioInaccesible para el usuario
Se envía en CADA petición (cabecera Cookie:)El cliente solo envía el id de sesión (PHPSESSID)
Tamaño limitado (~4KB)Sin límite práctico
Para preferencias no sensibles (idioma, tema...)Para datos sensibles (login, carrito...)
Idea clave: incluso al usar sesiones, hay UNA cookie por debajo: PHPSESSID=abc123.... Esa cookie SOLO contiene el id; los datos reales están en el servidor en /tmp/sess_abc123....

3. Sesiones en PHP — flujo básico

// 1. Iniciar la sesión (antes de cualquier salida)
session_start();

// 2. Leer/escribir como cualquier array
$_SESSION['user_id'] = 42;
$_SESSION['login']   = 'pablo';
$_SESSION['carrito'] = ['pelicula_1','pelicula_5'];

// 3. Más tarde, en otra página:
session_start();
echo $_SESSION['login'];   // 'pablo'
session_start() DEBE llamarse antes de cualquier output (echo, espacios fuera de <?php, etc.). PHP necesita enviar la cabecera Set-Cookie con el PHPSESSID; si ya hay output, las cabeceras están enviadas → warning "headers already sent".

4. Cerrar sesión correctamente

session_start();
$_SESSION = [];                  // 1. Vaciar el array en memoria
session_unset();                  // 2. (redundante, pero por costumbre)
session_destroy();                // 3. Destruir el archivo del servidor

// 4. (Opcional) borrar la cookie PHPSESSID del navegador
if (ini_get("session.use_cookies")) {
    $p = session_get_cookie_params();
    setcookie(session_name(), '', time()-42000, $p["path"], $p["domain"], $p["secure"], $p["httponly"]);
}

5. Cookies en PHP

// Crear/actualizar una cookie
setcookie(
    'tema_preferido',     // nombre
    'oscuro',             // valor
    time() + 60*60*24*30, // expiración (timestamp Unix) — 30 días
    '/',                  // path (a qué rutas se envía)
    '',                   // domain (vacío = dominio actual)
    true,                 // secure → solo se envía por HTTPS
    true                  // httponly → no accesible desde JavaScript
);

// Leer
echo $_COOKIE['tema_preferido'] ?? 'claro';

// Borrar (poniendo expiración en el pasado)
setcookie('tema_preferido', '', time() - 3600, '/');
Flags de seguridad importantes:
  • HttpOnly → JS (document.cookie) NO puede leer la cookie. Mitiga XSS.
  • Secure → la cookie solo se envía por HTTPS, nunca por HTTP claro.
  • SameSite=Strict/Lax → mitiga CSRF (la cookie no se envía en requests cross-site).

6. Seguridad: session fixation y session_regenerate_id

Ataque: un atacante consigue que la víctima use un PHPSESSID que él conoce (p. ej. pasándolo por URL). Cuando la víctima se loguea, el atacante ya tiene su sesión.

Defensa: al iniciar sesión exitosamente, regenerar el id:

// Después de validar usuario y contraseña:
session_regenerate_id(true);   // true = destruye la sesión vieja
$_SESSION['user_id'] = $id;

7. Control de inactividad

Cerrar sesión automáticamente tras X minutos sin actividad:

session_start();
$inactividad_max = 30 * 60;  // 30 minutos

if (isset($_SESSION['ultimoacceso']) && time() - $_SESSION['ultimoacceso'] > $inactividad_max) {
    session_unset();
    session_destroy();
    header('Location: login.php?expirado=1');
    exit;
}
$_SESSION['ultimoacceso'] = time();  // Actualizar marca de tiempo

(En tu DWES03 lo aplicas justamente así.)

9. Configuración relevante de php.ini (saber que existe)

  • session.cookie_lifetime → duración de la cookie PHPSESSID (0 = sesión del navegador).
  • session.gc_maxlifetime → tiempo de vida de los datos en el servidor.
  • session.cookie_httponly = 1, session.cookie_secure = 1 → seguridad por defecto.

2. Namespaces — separar nombres iguales

Sin namespaces, no podrías tener dos clases llamadas Pelicula en el mismo proyecto (una tuya, otra de una librería). Los namespaces resuelven eso.

class Pelicula {
    // ...
}

// Otro archivo que la usa:

3. PSR-4 — autoload basado en namespaces

PSR-4 mapea un prefijo de namespace a un directorio base. Composer genera un autoloader que, cuando PHP encuentra una clase, hace la transformación:

Mapping en tu composer.json: "PCH04\\": "srcpch/"

Cuando PHP necesita PCH04\modelo\Pelicula:
1. Quita el prefijo PCH04\ → queda modelo\Pelicula
2. Sustituye las barras invertidas por barras: modelo/Pelicula
3. Añade .php y le pone el directorio base: srcpch/modelo/Pelicula.php

Patrón arquitectónico para separar responsabilidades:

  • El controlador NUNCA hace SQL directo. Pide al modelo.
  • El controlador NUNCA hace echo de HTML. Eso es la vista.
  • El modelo NUNCA accede a $_POST, $_GET. Esos son del controlador.

Permite separar la lógica PHP del HTML. El controlador "asigna" variables, la plantilla las usa con sintaxis propia.

📚 Teoría · API REST y consumo con Guzzle

1. ¿Qué es REST?

REST (Representational State Transfer) es un estilo arquitectónico para APIs que se apoya en HTTP. Principios:

  • Recursos identificados por URLs (/peliculas/42).
  • Verbos HTTP que describen la operación (GET para leer, POST para crear...).
  • Sin estado: cada petición es independiente, el servidor no guarda contexto entre peticiones.
  • Representaciones: normalmente JSON (antes era XML).

2. Verbos HTTP y su semántica

VerboSignificadoIdempotenteEjemplo
GETLeer recurso(s)SíGET /peliculas
POSTCrear recurso nuevoNoPOST /peliculas
PUTReemplazar recurso completoSíPUT /peliculas/42
PATCHActualizar parcialmenteSí*PATCH /peliculas/42
DELETEEliminar recursoSíDELETE /peliculas/42

Idempotente: ejecutar la misma operación N veces produce el mismo resultado que ejecutarla una sola vez. GET, PUT, DELETE deben serlo. POST no (cada vez crea un nuevo recurso).

3. Códigos de estado HTTP

use Illuminate\Http\JsonResponse;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Validator;

public function update(Pelicula $pelicula, Request $request): JsonResponse
{
    // 1. Comprobar que el body es JSON
    if (!$request->isJson()) {
        return response()->json(['error'=>'Se esperaba JSON'], 403);
    }

    // 2. Validar
    $v = Validator::make($request->json()->all(), [
        'titulo' => 'required|string|max:60',
        'anio'   => 'required|integer|min:1900',
    ]);
    if ($v->fails()) {
        return response()->json(['errores'=>$v->errors()], 422);
    }

    // 3. Ejecutar
    $datos = $v->validated();
    $pelicula->fill($datos)->save();

    // 4. Responder
    return response()->json(['ok'=>true, 'pelicula'=>$pelicula], 200);
}
response()->json()

Genera una respuesta con Content-Type: application/json. Le pasas un array PHP y Laravel hace el json_encode internamente. No hagas json_encode antes — sería doble codificación.

return response()->json($array, 200);     // Bien
return response()->json(json_encode($array), 200);  // MAL (doble JSON)
$request->validate vs Validator::make
  • $request->validate([...]): si falla lanza excepción → respuesta automática 422 (en API) o redirect con errors (en web). Cómodo.
  • Validator::make(...): NO lanza excepción. Te devuelve un objeto que consultas con ->fails() y ->errors(). Más control.

📚 Teoría · AJAX y JAXON

1. ¿Qué es AJAX y por qué se usa?

AJAX = Asynchronous JavaScript And XML (aunque hoy normalmente se intercambia JSON, no XML). Es una técnica para que el navegador haga peticiones HTTP al servidor sin recargar la página entera, recibiendo solo los datos necesarios y actualizando dinámicamente partes del DOM.

Aplicación tradicionalAplicación AJAX
Cada acción del usuario → request → el servidor devuelve TODA la página HTML otra vez → recarga completaCada acción → request asíncrono → el servidor devuelve solo los datos/HTML del trozo afectado → el JS actualiza solo esa parte del DOM
Más lento, parpadeo visualMás rápido, experiencia fluida
Más tráfico de red (HTML repetido)Menos tráfico

2. ¿Qué es JAXON?

JAXON es un framework PHP+JS que automatiza la mayor parte del trabajo de hacer AJAX. Está dividido en dos partes:

  • JAXON-PHP: librería del servidor. Permite registrar funciones PHP "AJAX-callable" que el cliente puede invocar.
  • JAXON-JS: librería JavaScript del cliente. Genera automáticamente funciones JS (jaxon_NOMBRE) que, al llamarlas, disparan una petición AJAX al servidor.
La gracia: tú no escribes nada de fetch/XMLHttpRequest. Defines una función PHP, la registras, y JAXON crea el "puente" para llamarla desde JS.

8. La clase Response — comandos para el cliente

Una función registrada DEBE devolver una Response. El objeto acumula "comandos" que JAXON-JS ejecutará en el navegador al recibir la respuesta.

$response = new Response();

// Modificar el DOM por id
$response->assign ('idDiv', 'innerHTML', '<p>Nuevo contenido</p>');   // REEMPLAZA
$response->append ('log',   'innerHTML', '<div>Mensaje</div>');       // AÑADE AL FINAL
$response->prepend('log',   'innerHTML', '<div>Mensaje</div>');       // AÑADE AL PRINCIPIO
$response->clear  ('idDiv', 'innerHTML');                              // VACÍA

// Modificar atributos / estilos
$response->assign('idDiv', 'style.display', 'none');
$response->assign('idInput', 'value', '');

// Interacción con el usuario
$response->alert('¡Operación completada!');
$response->confirm('¿Estás seguro?', 'borrarPelicula', 42);
$response->redirect('otra_pagina.php');

// Ejecutar JS arbitrario
$response->script('console.log("hola desde el servidor")');
$response->call('miFuncionJS', $arg1, $arg2);

return $response;

9. Flujo completo de una llamada AJAX con JAXON

1. Usuario pulsa botón → onclick ejecuta jaxon_borrarPeliculaPCH(42) (JS generado por rq()->call()).
2. JAXON-JS hace POST a backend.php con la info de la llamada.
3. backend.php ve canProcessRequest() = true → processRequest().
4. JAXON-PHP localiza borrarPeliculaPCH entre las registradas y la invoca con (42).
5. La función ejecuta SQL, modifica el Response con assign/alert/etc, devuelve $response.
6. JAXON-PHP serializa el Response a JSON (los "comandos") y los devuelve.
7. JAXON-JS recibe el JSON y ejecuta los comandos en el DOM del navegador (sin recargar).

10. Ventajas vs limitaciones

Ventajas:

  • UI más rápida y fluida (solo se actualiza lo necesario).
  • Menos tráfico (no se reenvía HTML completo).
  • Permite interacciones ricas (validación al vuelo, autocompletado, drag&drop con persistencia, etc.).

A tener en cuenta:

  • Más dependencia del JS — si está desactivado, la app no funciona.
  • SEO limitado en contenido cargado por AJAX (los buscadores ven la página inicial).
  • Conviene mantener un fallback tradicional para accesibilidad.

11. Si retornas algo que no es Response...

Si una función registrada hace return "ERROR"; en lugar de devolver Response, JAXON-JS recibe una cadena que no tiene el formato esperado de comandos → ignora la respuesta, el DOM no cambia. No falla visiblemente, pero la acción del usuario parece no haber hecho nada.
